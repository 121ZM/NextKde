# R1 · data-service `activity.snapshot` map 竞争 panic

| 字段 | 值 |
|---|---|
| 阶段 | 一 |
| 并发组 | A（与 R2/R3 同 `main.go`，串行） |
| 依赖 | 无 |
| 优先级 | P0（必然 panic） |
| 分支 | `fix/2026-09-20-ds-activity-race` |

## 问题
`services/data-service/main.go:947-952` 中 `activity := s.state.Activity` 只浅拷贝结构体，`TodayApps`/`UptimeByDay` 两个 map 头仍指向活跃 map。`main.go:1059` 的 `json.Marshal(response)` 在锁外迭代它们；而 `settleTick` 每秒在锁内写 `TodayApps`（`main.go:881-883`），`rollDay` 每天重建 map（`main.go:850`）。Go 运行时对 "concurrent map iteration and map write" 直接 **fatal panic，不可 recover**。QML 轮询 `activity.snapshot` 即触发。

`weather.snapshot`（`main.go:966-971`）同类较轻：`Locations` slice 元素被 `setWeatherLocation` 原地改写（`weather.go:457`），锁外 marshal 读撕裂数据，-race 报但不 panic。

## 改动点
- marshal 移入 `s.mu` 锁内，或锁内深拷贝 `TodayApps`/`UptimeByDay` 后锁外 marshal。
- `weather.snapshot` 同样处理（深拷贝 Locations 或锁内 marshal）。
- 注意：锁内 marshal 不得做阻塞 IO；map 拷贝要完整（嵌套结构）。

## 建议
```go
case "activity.snapshot":
    s.mu.Lock()
    raw, err := json.Marshal(map[string]any{"activity": s.state.Activity})
    s.mu.Unlock()
    if err != nil { return dataError(...) }
    return DataResponse{Result: json.RawMessage(raw)}
```

## 验证
- 新增 `-race` 用例：goroutine 并发 `settle`/`rollDay` + 循环 `activity.snapshot`，断言无 panic。
- `go test -race ./services/data-service/`。

## 审查要点
- 锁内 marshal 是否含阻塞调用；深拷贝是否漏掉嵌套 map/slice。
- 是否引入新锁顺序问题（与 R2 的 conn 写锁分开）。
