# R2 · data-service conn 写路径无统一互斥 → JSONL 交错 / 广播死锁

| 字段 | 值 |
|---|---|
| 阶段 | 一 |
| 并发组 | A（依赖 R1，同 `main.go` 串行） |
| 依赖 | R1 |
| 优先级 | P0 |
| 分支 | `fix/2026-09-20-ds-conn-writelock` |

## 问题
三条写路径共用一条 conn：
- `subscribeDesktop` 首事件（`main.go:237`）
- `publishDesktop`/`publishWeather` 广播（`main.go:258,280`，持 `desktopSubscribersMu`）
- 请求-响应写（`main.go:1064`，**不持任何锁**）

注释（`main.go:269`）声称同一互斥防交错，但响应写没拿 → 广播可与响应**字节级交错**，下行 JSON 永久损坏一行。更糟：`SetWriteDeadline` 跨 goroutine 竞争——`subscribeDesktop` 在 `:241` 清 deadline，可与 `publishDesktop` 在 `:254` 设 deadline、`:258` 写之间交错 → 对已死 conn 的写**无 deadline 无限阻塞**，且持有 `desktopSubscribersMu` → 之后所有 publish/subscribe 卡死，事件系统整体死锁。

## 改动点
- 每个 conn 一个写 goroutine + buffered channel，或给 conn 包 `struct{ net.Conn; wmu sync.Mutex }`，所有写与 deadline 操作走 `wmu`。
- 收编 `subscribeDesktop`/`publishDesktop`/`publishWeather`/响应写四处。
- 持 `wmu` 期间不持 `desktopSubscribersMu` 做长阻塞写（避免死锁）。

## 验证
- 构造快广播 + 慢/死 conn 压测，断言无交错、无整体卡死。
- `go test -race`。

## 审查要点
- 锁粒度：`wmu` 与 `desktopSubscribersMu` 顺序，防 ABBA。
- 死 conn 清理与 subscriber 移除是否仍正确。
