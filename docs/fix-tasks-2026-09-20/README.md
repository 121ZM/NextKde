## 工作流程（强制）

1. 从 `ROADMAP.md` 取任务，**先读 `CONSTRAINTS.md`** 和该任务卡 `tasks/R*.md`。
2. **创建本地分支**再动手（见下"分支与 PR"）。每个任务独立分支，不夹带无关改动。
3. 实现修复（只改该任务范围）。
4. 构建 + 验证（见 CONSTRAINTS.md §验证、任务卡"验证"）。
5. **必须调用只读子代理审查**：把 `git diff` 交给 `code-reviewer` 复核，
   结论随提交信息留档。发现问题→修复→再审，直到通过。
6. 更新 ROADMAP 状态 + 任务卡勾选 + ACCEPTANCE 记录 → 提交。

## 子代理执行规则（强制）

- **每个任务的实现都用子代理执行**（`fixer`），不把实现写在本代理上下文里做苦力；
  本代理负责拆解、下发规格、汇总、送审。
- **能并发就并发**：无文件重叠、无依赖的任务放进同一批 `Task` 调用并行跑。
- **并发任务之间不得冲突**：同一批里不允许两个子代理改同一个文件
  （并发冲突矩阵见 ROADMAP §并发分组）。
- **有依赖就串行**：依赖另一任务产物（如 daemon 先提供 op）的任务排后续阶段，
  不得与上游任务同批并发。
- 每个 `fixer` 任务卡必须自带：目标文件、改动点、不得触碰的范围、验证命令、
  以及"完成后把 diff 交回"的要求。
- **实现 ≠ 完成**：`fixer` 跑完验证只是"实现完成"，**不**算任务完成。本代理
  收到 diff 后必须再发一个只读 `code-reviewer` 子代理审查，通过才算完成；
  未通过则把意见回给 `fixer` 修，再审，直到通过。不得跳过、不得本代理自审替代。

## 分支与 PR 规则（强制）

- 本地工作分支：`fix/2026-09-20-<slug>`，**从上游 `origin/main` 干净拉取**，
  不从上一轮或本阶段其它分支拉。
- 推送到 `fork`（skjsbsnq/NextKde），向 `origin`（SuceV587/NextKde）上游提 PR。
- **按阶段提 PR**：每完成一个阶段合并一次；一个阶段可含多个任务分支。
- **阶段隔离**：阶段 N+1 的分支从 `origin/main`（或其已合并点）拉，
  **不得**把阶段 N 的未合并 commit 带进来；阶段 N 的 PR 也不得混入阶段 N+1 的改动。
  - 若阶段 N+1 的某任务**硬依赖**阶段 N 已合并的代码，必须等阶段 N PR 合并后再拉分支。
  - 禁止在一条长链上堆叠多个阶段的 commit。
- commit message 遵循仓库风格 `fix(scope): …`，关注 why。
